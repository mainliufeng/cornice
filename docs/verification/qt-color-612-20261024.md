# Qt 6.12 Color collision: baseline reproduction and closure

The initial full-lock test failed its existing log assertion in the media and
polkit QML. An untouched `git archive 14d6b79` baseline was tested under the same
Qt 6.12.0, read-only native QML modules and private compositor as the candidate.
No production UI, current compositor, system bus, input or settings were used.

QtQuick's installed `plugins.qmltypes` exports a new singleton `QtQuick/Color
6.12` (`QQuickColor`). In an offscreen baseline probe, unqualified `Color` had an
`rgba` function but no `foreground`. Merely versioning `qs.Commons 1.0` did not
fix lookup. A QtQuick 6.11 import or the explicit `Commons.Color` alias resolved
the unchanged project's `#c9d1d9` theme color. This establishes a QML import
collision independently of Broker/compositor task logic.

The full unchanged baseline shell reproduced all three original media/polkit
TypeErrors and undefined-to-QColor assignments. After real bar IPC geometry was
ready, its empty bar pixel was white `[255,255,255]`. The candidate's same pixel
was the exact mono theme `[13,17,23]` and no QML errors remained. The regression
requires actual geometry readiness and the expected theme value, so an initial
black frame or compositor notice cannot pass as a rendered theme.

The fix only adds `import qs.Commons as Commons` and qualifies theme access as
`Commons.Color.*` in 55 files (352 references). `Color.qml`, theme values, public
exports, layout, input and authentication logic are unchanged. A reverse-text
comparison against `c310022` verifies the exact mechanical scope in
`evidence/color-mechanical-review.json`. Existing third-party plugins should
likewise qualify this singleton when using QtQuick 6.12.
